# Contour UI Agent Instructions

These instructions apply to the entire frontend repository.

## Engineering skill

For every frontend software-development task, read and apply
`.agents/skills/staff-frontend-engineer/SKILL.md` unless the user explicitly
disables it. Scale analysis and verification to the actual risk.

## Required context

Before frontend implementation, read in order:

1. `docs/project-scope.md`;
2. `docs/architecture/frontend.md`;
3. `docs/development/roadmap.md`;
4. `docs/quality/testing.md`; and
5. `contracts/README.md` for API-facing work.

Use `README.md` for the public repository summary. These local documents and
the current code control frontend implementation. Private parent-workspace
planning may supply product intent, but it must not be copied here or treated as
evidence that a backend capability ships.

## Current objective

Phase 0 is active. Build the smallest honest browser shell for the
source-to-evidence workflow. Only the health endpoints exist today. Later
navigation may be visible as unavailable, but must not imply that planned
workspace, source, ingestion, search, entity, evidence, or run APIs exist.

## Execution workflow

For roadmap-driven work without a more specific user request, use `TASKS.md` as
the bounded execution queue.

- Claim one `ready` card and keep its owner, assignee, status, and handoff
  current.
- Work on at most one card at a time. Do not start dependency-blocked follow-up
  work without an explicit coordinator decision.
- Stop in `review` when checks pass, or `blocked` with concrete evidence.
- An explicitly assigned reviewer accepts work, records it in
  `docs/development/task-history.md`, and controls queue refill or reordering.
- A specific user request may supersede the queue; do not add it unless the user
  or coordinator requests bookkeeping.

## Repository boundary

This repository owns the browser application, frontend components, client-side
behavior, frontend API adapter, generated TypeScript contract types, browser
tests, frontend configuration, and implementation-coupled documentation.

Do not add Python backend behavior, database access, backend authorization, or
copies of private planning/research. Do not import code or Python types from the
backend repository.

## API contract discipline

- `contracts/contour.openapi.json` is the pinned frontend snapshot.
- The source contract is generated by the backend and is never hand-edited.
- Run `scripts/check-backend-contract.sh` before API integration and after a
  backend contract change. Use `scripts/sync-backend-contract.sh` only when the
  coordinated backend artifact is intentionally accepted.
- Centralize base URL, endpoint paths, transport, wire types, response
  validation, cancellation, and error mapping in the frontend API boundary.
- Do not invent endpoints, request shapes, or response fields from plans.
- Contract changes that break the frontend require linked backend, frontend,
  and integration tasks with an explicit migration or versioning decision.

## Implementation discipline

- Prefer strict TypeScript and an App Router application for the initial
  scaffold unless an accepted local decision states otherwise.
- Prefer Server Components and keep client boundaries small.
- Treat loading, empty, error, retry, unavailable, responsive, and accessible
  states as part of correctness.
- Use semantic HTML, keyboard-operable controls, visible focus, labels, useful
  errors, and design tokens.
- Keep server data separate from local UI state; avoid duplicated server state
  and scattered endpoint strings.
- Treat browser-controlled input and API data as untrusted. Backend checks
  remain authoritative for authorization and data integrity.
- Preserve unrelated changes and avoid abstractions for future phases that are
  not in the current task.

## Verification and documentation

Follow `docs/quality/testing.md`. Run the smallest relevant format, lint, type,
test, contract, and browser checks that give confidence proportional to risk.
Record checks that could not run.

Update docs when a contract or accepted frontend boundary changes. State
implemented and planned behavior accurately. Keep setup in `README.md`,
accepted boundaries in architecture docs, and completed task evidence in the
task history.
